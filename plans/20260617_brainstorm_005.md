# Item 005 (Phase 2) — Characterize & damp the post-withdrawal hover oscillation

## Context

Phase 1 built the staged-startup machinery in
`examples/rotor_hover_pressure_comparison.jl` (4-phase smoothstep freestream pulse
+ ENV hooks `MAGVINF_PEAK/END`, `FREESTREAM_RAMP/HOLD/WITHDRAW_REVS`,
`SETTLE_REVS`, `TRUNCATION_DEPTH_R`, `BERNOULLI_ONLY`, run-length bookkeeping,
plateau diagnostics) plus driver `examples/run_rotor_hover_stable_wake.sh`. It
showed the staged startup **kills the impulsive startup ring**, but after the
freestream is withdrawn to hover (`magVinf=0`) a CT oscillation appears.

**I overcalled that oscillation "intrinsic / non-damping / growing."** Re-reading
the `data/stable_wake_iter4` settle window (rev 4.3 peak 0.087 → rev 5.87 trough
0.075 → rev 7.87 peak 0.094 → descending) shows a **clean, regular oscillation of
period ≈ 3.5 rev**, but riding on a **rising mean** (withdraw relaxation + wake
column still developing) and spanning only **~1.3 cycles** — far too few to decide
whether amplitude grows, holds, or decays. The run also used aggressive
`TRUNCATION_DEPTH_R=2`, which may itself shape the oscillation. The user is right
to be skeptical.

**This phase answers, with data:** (1) how consistent are period & amplitude over
many cycles; (2) does a more gradual ramp/withdrawal reduce it; (3) run out
longer — does it damp; (4) is it a truncation artifact; and produces (5) a menu
of damping mechanisms (physical first, numerical as second resort), with the top
physical candidates tested.

## Experiments

### E1 — Long run: period & amplitude consistency, damping (answers Q1 & Q3)
Extend the settle phase hard so we capture **many** cycles of the ~3.5-rev
oscillation. Config: same staged startup (spinup 1.5 @0.4×RPM, peak 5, ramp 1,
hold 1.5, withdraw 3), `SETTLE_REVS≈30`, `TRUNCATION_DEPTH_R=1`, `NT=12` for speed.
~9 cycles. Analysis (read the per-step force CSV `monitors/..._force_system1.csv`):
- **Detrend** the rising mean (low-order polynomial / moving average over one
  period) then measure peak-to-peak per cycle.
- Tabulate successive peak times → period consistency; successive detrended
  amplitudes → growing / steady (limit cycle) / decaying.
- Verdict: decaying ⇒ it's a long transient (good, just needs more revs);
  steady ⇒ limit cycle; growing ⇒ instability.

### E2 — Truncation-depth control: is the oscillation a truncation artifact? (Q4 + de-risks E1)
Matched schedule, sweep `TRUNCATION_DEPTH_R = 1 / 2 / 4` (3 parallel runs).
- If **period scales with depth** (deletion-front transit time) or amplitude
  changes qualitatively ⇒ truncation is shaping it; depth=1 results are suspect
  and we must characterize at ≥4R.
- If **period/amplitude are insensitive to depth** ⇒ depth=1 is a safe fast
  proxy and the oscillation is a wake-physics phenomenon, not a boundary artifact.
This run gates trust in all the depth=1 iteration the user requested.

### E3 — Ramp/withdrawal gradualness sweep (answers Q2)
Sweep `FREESTREAM_WITHDRAW_REVS = 2.5 / 6 / 12` (3 parallel, depth from E2 verdict),
plus a **pure-spinup control** (`MAGVINF_PEAK≈0`, no freestream pulse — isolates
whether the freestream pulse itself is what later rings). Compare detrended
settle-window amplitude.
- Slower withdrawal **shrinks** amplitude ⇒ withdrawal-excited transient (the
  ramp is the lever; tune it further).
- Amplitude **independent** of withdrawal rate ⇒ self-sustained, set by the hover
  wake itself ⇒ damping mechanisms (E4) are the lever.

### E4 — Damping-mechanism menu (test ALL schemes)
**Sequencing (user directive):** first lock in the **best non-oscillating
baseline** achievable from E1–E3 (the schedule/truncation/withdrawal combination
that gives the smallest detrended settle amplitude *without* extra damping). Only
then run E4, applying **each** damping scheme below as a single-variable change on
top of that baseline, and rank them by detrended-amplitude reduction (and by how
much each distorts the mean CT / wake structure). Test all of them, physical
first; numerical ones are reported as second resort even if effective.

Note: viscous core spreading and SFS are **already on** in the baseline (user
directive); E4.1/E4.2 test *stronger* settings, and the SFS on↔off contrast is a
diagnostic of how much the existing SFS is already damping.

**Physical**
1. **Viscous diffusion ↑** — `WAKE_NU` (FLOWVPM `CoreSpreading`, on by default at
   ~1.69e-5/ρ). Raising effective viscosity spreads/dissipates tip-vortex
   gradients. Most physical knob (Reynolds-number based). Test: `WAKE_NU` ×3, ×10.
2. **Subfilter-scale (SFS) model** — on by default (`DynamicSFS`); strengthen via
   `SFS_MAXC`/`SFS_RLXF`. Also run one `SFS_OFF=true` purely to *measure* how much
   the existing SFS already damps. Right tool if the oscillation is a small-scale
   pairing instability.
3. **Kernel overlap / core growth** — `overlap` (currently 3.0), `WAKE_CORE_BETA`
   (1.5), `core_size`. Under-overlapped particles produce spurious velocity noise;
   ensuring overlap is a physical-regularization fix, not added dissipation.
4. **Wake resolution** — `NT` (steps/rev) and `p_per_step`. Diagnostic as much as
   cure: if refining **removes** the oscillation it was an under-resolution
   artifact; if it **sharpens/persists** it is physical (e.g. helical-wake
   leapfrog/pairing, a real hover-wake instability) — then damp, don't "fix".

**Numerical (second resort)**
5. **Vortex relaxation** — Pedrizzetti / corrected-Pedrizzetti scheme
   (`PARTICLE_RELAX`, default on; rlxf 0.3). Realigns Ω with local velocity;
   strengthening suppresses spurious modes at some physical cost.
6. **Particle merging** — `MERGE_PARTICLES`, merge radius `merge_r_factor`.
   Coarsening = numerical dissipation.
7. **Larger target kernel regularization** — `kerneloffset_targets` /
   `WAKE_CORE_SIZE`; smooths the induced field feeding the body.
8. **Loading/feedback low-pass (new code)** — under-relax the body bound
   circulation (or the wake-induced velocity fed to the body) between steps:
   `Γ_n = (1-α)Γ_{n-1} + α Γ_solve`. Purely artificial damping of the
   body↔wake feedback loop; cheap, last resort. Implement behind an ENV flag
   (e.g. `BOUND_STRENGTH_RLX=α`, default 1.0 = off) applied to `body.strength` in
   the simulate loop after each solve.

**E4 run matrix** (all on top of the E1–E3 best non-damping baseline, one
variable each): `baseline`, `nu_x3`, `nu_x10`, `sfs_strong` (raise SFS_MAXC/RLXF),
`sfs_off` (diagnostic), `overlap_hi`, `corebeta_hi`, `nt_hi` (resolution),
`pps_hi` (resolution), `relax_strong`, `merge_aggressive`, `kernoff_hi`,
`bound_rlx`. Run in budget-respecting batches; rank by detrended settle-amplitude
reduction. Report the full ranked table (the deliverable menu with measured
effect), flagging which are physical vs numerical.
