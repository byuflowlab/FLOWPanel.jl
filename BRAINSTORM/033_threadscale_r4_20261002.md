# p033 R4 thread-scaling campaign (2026-10-02) — FGS vs ILU-GMRES-nfcache, fixed knobs

Ryan's ask (2026-10-02): thread-scaling head-to-head at **R4 only**,
j ∈ {1, 8, 16, 32, 64}, latest FGS (threaded setup, 033 B-I2) vs
`krylov_ilu_nfcache`, **no re-tuning** — the certified R4 j64 knob set is
transplanted to every thread count (explicitly against the 021 trap-list
letter; every CSV row records the knobs, the harvest labels the transplant).
Two job families:

- **Job A (cold)** `benchmark/run_p033_ts_cold_r4.slurm.sh` — array 0-4 over j.
  FGS arm = `fgs_setup_ab.jl` (ARMS=old,new, CERT_SOLVE=1, AB_SOLVE_K=3):
  serial-vs-threaded full ctor + bitwise certs + cold-solve rows (new in this
  campaign: cold_solve rows persisted to the CSV). ILU arm =
  `rotor_hover_solver_phase2.jl` (CONFIGS=krylov_ilu,krylov_ilu_nfcache,
  MEM_BUDGETS=500) at **pre-seeded** `tune_phase2.csv` knob rows written by
  the launcher (budget 0 = P15/MAC0.55/leaf21, budget 500 = P12/MAC0.55/leaf48
  — the 2026-09-22 certified rows), so `phase2_knobs()` resolves with no
  tuner pass.
- **Job B (warm rotor hover)** — 021 winB protocol under the **018-ported
  wake physics** (`WAKE_ENV_018=1`, new `benchmark/p033_wake_env_018.jl`;
  defaults only, env wins; Das-table sha256 preflight). The ported physics
  changes the case, so the 2026-09-24 R4 checkpoints are INVALID here:
  `run_p033_ts_ckpt_r4.slurm.sh` (array 0-1 = family) regenerates both family
  checkpoints at j=64 (108 steps, VTK, campaign-qualified names
  `p033ts_R4_ckpt_{fgs,ilu}`), then `run_p033_ts_winb_r4.slurm.sh`
  (array 0-4 over j, `--dependency=afterok:<ckpt>`) runs `fgs_proj2` +
  `ilu_nfcache_proj2` rev-4 restart legs per j.
