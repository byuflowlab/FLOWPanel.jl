## 2. `scripts/p022_harvest.py` — NEW (Python 3, stdlib only)

**Purpose:** compute 022's M1 metric, matched IGE/OGE thrust ratios, and the
CSVs backing the Phase 5 figure — for runs that never finished.

Exists rather than reusing `scripts/p018_analyze.py` because that script pins
`RPM_DEFAULT = 5400` inside its force-monitor fallback with no CLI
pass-through. 022 runs at RPM 6000, and the fallback is the load-bearing path
here: `<tag>_CT_vs_rev.csv` is only written after the time loop completes, so a
walled or cancelled run leaves none. Shared helpers (`DATA`, `per_rev`,
`_mean`, `_std`, `PLACEHOLDER_TOL`) are imported from `p018_analyze` rather
than duplicated.

Subcommands:
- `m1 RUN [--revs LO HI] [--rpm]` — per-rev block means, cycle-mean ± cycle-std
  (n−1 across block means, matching the driver's own definition).
- `ratio IGE_RUN OGE_RUN [--revs LO HI]` — matched ratio, uncertainty
  propagated in quadrature, reported both cycle-std-based and SEM-based.
- `figdata [--out DIR] [--point H IGE OGE LO HI]...` — writes
  `experiment.csv`, `theory_cb.csv`, `sim.csv`.

Three guards, each added in response to something actually observed:
- **Blow-up guard** — any |CT| > 1 step is excluded and reported loudly with
  its step and rev, plus "any window reaching it is NOT harvestable". Without
  it the single CT ≈ 372 step in `p022_ige_coarse` swamps any mean containing
  it.
- **Partial-window guard** — warns which revs of the requested window are
  absent, and separately warns when fewer than 2 blocks make cycle-std
  meaningless. Caught a silent "std = 0.000000" from a one-block window.
- **Settled-vs-hover distinction** — `in_hover` (rev ≥ 6.5, post-withdrawal) is
  not the same as settled (rev ≥ 18, `SETTLE_REVS = 20`). Windows that clear
  the first but not the second are labelled preliminary.

Verified end-to-end against live cluster data: reproduces 0.075516 / 0.078888 /
ratio 1.0446 exactly, and the blow-up guard fires on steps 636–637.

## 8. Cluster disk cleanup — 432 G → 82 G

**Purpose:** bring `~/projects/FLOWPanel.jl` under the ~200 G budget recorded in
`ops_reference.md`.

Tool: `/tmp/trim_vtk.py` on the cluster (source kept in this session's
scratchpad; not committed — it is an ops utility, not project code). It groups
every per-step VTK file by step index across all series subdirectories of a run,
keeps the highest N (default 10), deletes the rest, and optionally rewrites the
`.pvd` indices. `monitors/`, `*.metadata.toml`, and all CSVs are never touched,
so every harvestable quantity survives.

Run in two passes:

| pass | runs | `.pvd` rewritten? | freed |
|---|---|---|---|
| 1 | 8 inactive runs, oldest first | yes | 127.4 G |
| 2 | 9 runs with live jobs | **no** | 226.3 G |
| | | **total** | **353.7 G** |

`p022_ige_coarse` (24 G) was deliberately excluded from both passes: it is the
subject of the active blow-up investigation and the cluster copy is the only
complete record beyond the 38 steps now on Ryan's laptop.

**Why pass 2 skips the `.pvd` rewrite:** the driver appends to the `.pvd` index
as each step is written, so rewriting it under a live job risks corrupting the
file. Dangling references to trimmed early steps are cosmetic (ParaView warns
and skips); a corrupted index is not. Those runs' indices will be complete but
reference missing early steps — regenerate or filter them at harvest if needed.

**Safety verification after the trim:** all 15 queued jobs still alive, and two
of three spot-checked runs had already written *new* steps past their keep
window (`p022_oge_coarse` at 703 with 693–702 kept; `p018_cs_f1_l2p4` at 767
with 757–766 kept), proving the trim did not interfere with writing. Monitor
directories intact in all three.

Result: **82 G total**, comfortably inside the budget.
